# Шаблоны воркфлоу n8n

Четыре воркфлоу, составляющие связку «Telegram ↔ панель». Импортируются как
есть; всё, что зависит от конкретного ВПН-сервиса, вынесено в **переменные n8n**,
поэтому для второго бота достаточно скопировать комплект и поменять три
значения.

| Файл | Что делает |
|------|-----------|
| `main-input.json` | Telegram Trigger → буфер → таблицы n8n → панель (`vpn_bot.incoming`) |
| `main-output.json` | Отправка в Telegram (текст, фото, стикер, голос) + подтверждение доставки |
| `outgoing-router.json` | Webhook от панели → ответ оператора, уведомления, синхронизация статусов |
| `ai-agent.json` | ИИ-агент с базой знаний и гейтом передачи оператору |

## Переменные n8n

Settings → Variables. Нужны, когда у ВПН-а свой отдельный бот. Если один бот
подключён к аккаунтам поддержки нескольких ВПН-ов, комплект воркфлоу один, а
сервис определяется по `business_id` из сообщения — `SERVICE_SLUG` тогда
используется только как запасной путь для обычных, не business, чатов.

| Переменная | Пример | Откуда взять |
|-----------|--------|--------------|
| `SERVICE_SLUG` | `gruvpn` | Настройки → Сервисы, поле «Слаг» |
| `TG_TOKEN` | `1234567890:AAF…` | @BotFather этого бота |
| `KB_COLLECTION` | `kb` | Настройки → Сервисы, «Коллекция Qdrant» |
| `PANEL_URL` | `https://admin.example.com` | адрес панели (`BASE_URL`) |
| `N8N_API_KEY` | случайная строка | тот же, что в `.env` панели |

Токен бота **не должен** быть вписан в URL нод: при ротации придётся править
десяток мест, и он утекает вместе с экспортом воркфлоу. Везде используется
`{{ $vars.TG_TOKEN }}`.

## Как панель узнаёт, чей это тикет

По `business_id` — это `business_connection_id`, который Telegram присылает с
каждым сообщением из аккаунта поддержки, подключённого к боту. Воркфлоу кладёт
его в событие, панель находит сервис сама (`app/rabbitmq_consumer.py`,
`_resolve_service`). Ничего сопоставлять в n8n не нужно.

Если `business_id` пустой — это обычный чат с ботом, и работает прежний путь:
сервис берётся из поля `service`, то есть из `$vars.SERVICE_SLUG`. Обе схемы
живут рядом, переключать ничего не надо.

**Неизвестный `business_id` панель отбрасывает** и пишет в лог, какой именно.
Это не поломка, а защита: тикет чужого ВПН-а лучше не принять, чем показать не
той команде. Увидели такую строку — впишите id в карточку сервиса.

## Порядок подключения нового ВПН-а

1. **Панель**: Настройки → Сервисы → «Добавить сервис». Четыре поля: название,
   адрес API бота, токен, `business_id`. Кнопка «Проверить подключение»
   покажет, какой бот ответил на этот токен, — жать до сохранения.
2. **Telegram**: подключить бота к аккаунту поддержки этого ВПН-а
   (Settings → Business → Chatbots) и взять оттуда `business_connection_id`.
3. **n8n**: если бот **один** на все аккаунты поддержки — комплект воркфлоу
   один, добавлять ничего не нужно, новый сервис заработает сам. Если у ВПН-а
   свой бот — скопировать комплект, поставить credentials этого бота и задать
   `TG_TOKEN`, `SERVICE_SLUG`, `KB_COLLECTION`.
4. Активировать воркфлоу.

Слаг, коллекция Qdrant и префикс ID диалогов заполняются сами и лежат в форме
под «Дополнительно». Менять слаг после первого запуска нельзя — он в ключах
Redis, в поле `service` и в имени коллекции.

## Что изменено под Telegram Business

- `Telegram Trigger` слушает и `message`, и `business_message`.
- Обращения к сообщению записаны как
  `($('Telegram Trigger1').item.json.message || …business_message)` — для
  обычных апдейтов поведение прежнее.
- В `user_message` и `callback` добавлено поле `business_id`.
- Внутренние ключи (Redis, `n8n_dialogs.service`) метятся
  `business_connection_id`, а при его отсутствии — прежним `SERVICE_SLUG`.
  Панель при синхронизации сверяет оба варианта, поэтому переход не ломает
  уже заведённые строки.
- Ответ в business-чат Telegram принимает **только** с
  `business_connection_id`. В `outgoing-router.json` нода
  `TG sendMessage с кнопками` его добавляет. Встроенная нода Telegram такого
  поля не имеет: если ответы operator → клиент идут через неё, её нужно
  заменить на HTTP Request к `sendMessage` по образцу той, что с кнопками.

## Проверка

1. Написать боту → тикет появился в панели **под нужным ВПН-ом**.
2. Ответить из панели → пришло в Telegram, в панели галочка доставки.
3. Отправить боту фото и голосовое → дошли, распознались.
4. Выключить ИИ в тикете → **после следующего сообщения клиента остался
   выключенным** (частая поломка: воркфлоу присылает не то поле).
5. Закрыть тикет в панели → в `n8n_dialogs` строка получила `status='closed'`.

## Контракт с панелью — не менять

- Очереди `vpn_bot.incoming` / `vpn_bot.outgoing`, путь вебхука
  `vpn-bot-outgoing`.
- Имя ноды `Распарсить JSON` — на неё ссылаются по имени.
- Поля `user_message`: `type, business_id, service, dialog_id, chat_id,
  user_username, user_name, message, ai_enabled, file_id, file_type`.
- Поля `delivery_confirmation`: `type, message_id, dialog_id, status, error`.
  Без них в панели не появятся галочки доставки.
- Значения `type` исходящих: `manager_message`, `send_to_user`,
  `operator_notify`.

Нужен `business_id` **или** `service` — по ним панель понимает, какому ВПН-у
принадлежит тикет. Если нет ни того, ни другого, всё сваливается в первый
сервис (`app/rabbitmq_consumer.py`, `_resolve_service`).
