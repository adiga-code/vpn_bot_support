# Шаблоны воркфлоу n8n

Четыре воркфлоу, составляющие связку «Telegram ↔ панель». Импортируются как
есть; всё, что зависит от конкретного ВПН-сервиса, вынесено в **переменные n8n**,
поэтому для второго бота достаточно скопировать комплект и поменять три
значения.

| Файл | Что делает |
|------|-----------|
| `main-input.json` | Telegram Trigger → буфер → таблицы n8n → панель (`vpn_bot.incoming`) |
| `main-output.json` | Отправка в Telegram (текст, фото, стикер, голос) + подтверждение доставки |
| `outgoing-router.json` | Webhook от панели → ответ оператора, уведомления, синхронизация статусов |
| `ai-agent.json` | ИИ-агент с базой знаний и гейтом передачи оператору |

## Константы: одна нода в начале воркфлоу

Первой нодой в каждом из четырёх воркфлоу стоит Code-нода **«Константы»**:

```js
const C = {
  TG_TOKEN: 'ТОКЕН_БОТА_ОТ_BOTFATHER',
  PANEL_URL: 'https://адрес-панели',
  N8N_API_KEY: 'та же строка, что в .env панели',
};
return $input.all().map((item) => ({ json: { ...item.json, ...C } }));
```

После импорта нужно открыть её и подставить три значения — по одному разу на
воркфлоу. Ниже на них ссылаются как `{{ $('Константы').first().json.TG_TOKEN }}`.

**Почему не Settings → Variables.** Раздел Variables (`$vars`) есть только на
платных редакциях n8n; в self-hosted community его нет вовсе, и
`$vars.TG_TOKEN` молча становится `undefined` — URL превращается в
`https://api.telegram.org/botundefined/…`, и отправка падает без внятной
ошибки. Переменные окружения (`$env`) тоже не подошли: их пришлось бы держать
в docker-compose всех трёх контейнеров и перезапускать n8n.

Нода отдаёт входящий элемент дальше **как есть**, только дописывая константы,
поэтому её вставка ничего ниже по цепочке не ломает.

**Что помнить:** значения лежат внутри воркфлоу и уедут вместе с его экспортом.
Не выкладывайте экспорт с заполненными константами в общий доступ, а при
ротации токена правьте четыре ноды — по одной на воркфлоу.

Всё, что зависит от конкретного ВПН-а (слаг, коллекция Qdrant), в константах
**не лежит** — оно приходит из панели, см. ниже.

## Пер-сервисное берётся из панели

Сразу за триггером стоит нода **«Диалог: resolve»** — один HTTP-запрос к панели:

```
POST {PANEL_URL}api/n8n/dialog/resolve      X-API-Key: {N8N_API_KEY}
{ "chat_id": "<chat.id>", "business_id": "<business_connection_id или ''>",
  "user_name": "<chat.first_name>", "user_username": "<chat.username>" }

→ { "dialog_id": "1189646670-1", "ai_enabled": true, "status": "ai",
    "is_new": false, "service_slug": "nemoivpn",
    "qdrant_collection": "kb_nemoivpn" }
```

Отсюда берётся всё пер-сервисное: слаг (ключи Redis, поле `service` в событиях
панели), коллекция Qdrant для ИИ-агента, номер тикета и флаг ИИ. Поэтому
**новый ВПН заводится формой в панели, и n8n трогать не нужно** — ни воркфлоу,
ни ноду «Константы».

Сервис панель ищет по `business_connection_id`; при пустом (обычный чат с
ботом) берётся первый активный — тем же порядком `sort_order, id`, каким
сортирует сервисы сама панель. Неизвестный `business_connection_id` — ответ
`404`: свалить чужой тикет в первый попавшийся ВПН хуже, чем не принять его.

### Почему именно так

Раньше диалог жил в двух базах сразу: у n8n своя таблица `n8n_dialogs`
(номер, `status`, `ai_status`, слаг), у панели своя `dialogs`, и они
синхронизировались встречными `UPDATE`-ами. Стоило им разойтись — n8n не
находил свою строку `WHERE user_id AND status='active' AND service=slug`,
делал `INSERT`, выдавал новый номер, и панель по этому номеру заводила
**второй тикет тому же клиенту**, пока первый висел открытым.

Теперь состояние одно. Личность диалога — пара (сервис, `chat_id`), владеет
ею панель, а инвариант «не больше одного незакрытого тикета на клиента»
держит уникальный индекс в БД (`dialogs_one_open_idx`). Resolve идемпотентен:
сколько угодно повторов дают тот же `dialog_id`; параллельные запросы — тоже.
Своих таблиц (`n8n_dialogs`, `n8n_messages`) у n8n больше нет — сообщения
пишет панель, когда получает их из `vpn_bot.incoming`.

## Порядок подключения нового ВПН-а

1. **Панель**: Настройки → Сервисы → «Добавить сервис». Четыре поля: название,
   адрес API бота, токен, `business_id`. Кнопка «Проверить подключение»
   покажет, какой бот ответил на этот токен, — жать до сохранения.
2. **Telegram**: подключить бота к аккаунту поддержки этого ВПН-а
   (Settings → Business → Chatbots) и взять оттуда `business_connection_id`.
3. **n8n**: ничего. Комплект воркфлоу один на все аккаунты поддержки, слаг и
   коллекцию он получает из resolve по `business_id`. Если у ВПН-а свой
   отдельный бот — скопировать комплект и поставить credentials этого бота;
   `TG_TOKEN` тогда свой в ноде «Константы» этого инстанса.

Слаг, коллекция Qdrant и префикс ID диалогов заполняются сами и лежат в форме
под «Дополнительно». Менять слаг после первого запуска нельзя — он в ключах
Redis, в поле `service` и в имени коллекции.

**Неизвестный `business_id` панель отбрасывает** (`404` на resolve, событие из
очереди — в лог) и пишет, какой именно id не опознан. Это не поломка, а защита:
тикет чужого ВПН-а лучше не принять, чем показать не той команде. Увидели такую
строку — впишите id в карточку сервиса.

## Что изменено под Telegram Business

- `Telegram Trigger` слушает и `message`, и `business_message`.
- Обращения к сообщению записаны как
  `($('Telegram Trigger1').item.json.message || …business_message)` — для
  обычных апдейтов поведение прежнее.
- В `user_message` и `callback` добавлено поле `business_id`.
- Внутренние ключи Redis метятся слагом из ответа resolve.
- Клиент везде опознаётся по `chat.id`, а не по `from.id`: в business-чате это
  разные люди — автором сообщения может быть владелец аккаунта поддержки.
- Ответ в business-чат Telegram принимает **только** с
  `business_connection_id`, а у встроенной ноды Telegram такого поля нет
  вообще. Поэтому в `main-output.json` три ноды отправки клиенту —
  `Send a text message`, `Send a photo message`, `Send a sticker` — переведены
  на HTTP Request к Bot API, как это давно сделано у `Голос: sendVoice`. Токен
  берётся из ноды «Константы», credentials этим нодам больше не нужны; имена,
  позиции и связи прежние, так что подтверждения доставки работают как
  работали.
- `business_id` протаскивается по всей цепочке: панель → вебхук →
  `outgoing-router` (Code-ноды «Подготовить файл» и
  «Нормализовать text→message») → входы `Main Output` → запрос в Telegram.
  Если он пустой, поле **не подставляется вовсе** — на пустую строку Telegram
  ругается. В JSON-теле это `Object.assign(…, business_id ? {…} : {})`, в
  multipart (фото, голос) — необязательный кусок query-строки в URL.
- Нода `Отправить оператору` осталась Telegram-нодой намеренно: уведомления
  операторам идут в обычный чат, business там ни при чём.

## Как устроен dialog_id

`<префикс сервиса><chat_id>-<номер обращения>`, например `nemoivpn_1189646670-2`
— второе обращение этого клиента. Префикс разводит одинаковые `chat_id` разных
ВПН-ов, номер растёт при каждом новом обращении после закрытия тикета.

Придумывает его только панель. Если в событие попадёт чужой или устаревший
номер, панель всё равно найдёт тикет по паре (сервис, `chat_id`) — второго не
появится.

## Проверка

1. Написать боту → тикет появился в панели **под нужным ВПН-ом**.
2. Ответить из панели → пришло в Telegram, в панели галочка доставки.
3. Отправить боту фото и голосовое → дошли, распознались.
4. Выключить ИИ в тикете → **после следующего сообщения клиента остался
   выключенным** (частая поломка: воркфлоу присылает не то поле).
5. Закрыть тикет в панели → следующее сообщение клиента заводит **новый**
   тикет (`…-2`), закрытый остаётся в истории.
6. Написать боту два сообщения подряд → оба в одном тикете, дублей нет.

## Контракт с панелью — не менять

- Очереди `vpn_bot.incoming` / `vpn_bot.outgoing`, путь вебхука
  `vpn-bot-outgoing`.
- Имя ноды `Распарсить JSON` — на неё ссылаются по имени.
- Поля `user_message`: `type, business_id, service, dialog_id, chat_id,
  user_username, user_name, message, ai_enabled, file_id, file_type`.
- Поля `delivery_confirmation`: `type, message_id, dialog_id, status, error`.
  Без них в панели не появятся галочки доставки. Текст `error` панель
  показывает оператору и по нему же запускает резервную отправку по MTProto,
  если та настроена (README, «Резервная отправка ответа»), — не глушите
  ошибку пустой строкой.
- Значения `type` исходящих: `manager_message`, `send_to_user`,
  `operator_notify`.
- События `operator_notify`: `new_dialog`, `operator_called`, `dialog_closed`,
  `ai_toggled`, `claim_requested`, `server_down`, `bot_down`. Незнакомое
  событие нода «Форматировать уведомление» выведет как есть — уведомление
  дойдёт, просто некрасивым.

Нужен `business_id` **или** `service` — по ним панель понимает, какому ВПН-у
принадлежит тикет. Если нет ни того, ни другого, всё сваливается в первый
сервис (`app/rabbitmq_consumer.py`, `_resolve_service`).
