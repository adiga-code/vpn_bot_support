# VPN Bot Support — Helpdesk Panel

Веб-панель оператора поддержки для VPN-сервиса. Работает в связке с Telegram-ботом через n8n: n8n принимает сообщения от пользователей и передаёт их в панель через Redis, операторы отвечают через веб-интерфейс, n8n доставляет ответы обратно в Telegram.

## Несколько ВПН-сервисов в одной панели

Панель обслуживает несколько ВПН-сервисов одновременно. Переключатель — ряд
пилюль под шапкой: слева «Все сервисы» со сводным счётчиком, дальше по пилюле
на каждый ВПН с количеством активных обращений («новые + непрочитанные»).

**Что у каждого сервиса своё:** диалоги и сообщения, база знаний (отдельная
коллекция Qdrant), промпт ИИ и промпт гейта, расписание, шаблоны, рассылки и
**вся вкладка «Автоматизация»** — включая лимит тикетов на оператора и грейс
офлайна. Общими остаются только учётные записи операторов и звуки.

**Доступ.** Оператору выдаётся флаг на сервис («Настройки → Операторы», колонка
«Доступ к ВПН»). Без флага он не видит диалоги этого ВПН-а ни в списке, ни по
вебсокету, не может отвечать по ним и не получает их тикеты в раздаче.
Администратор видит все сервисы автоматически, флаги ему не нужны.

**Слоты и грейс.** Загрузка считается по паре (оператор, сервис): оператор с
флагами на два ВПН-а набирает до `max_tickets_per_operator` в каждом. Грейс
офлайна тоже пер-сервисный — тикеты сервиса с грейсом 15 секунд вернутся в
очередь раньше, чем тикеты сервиса с грейсом 300.

**Бот-токены в панели не хранятся** — они остаются в n8n. Каждое исходящее
событие несёт поле `service` со слагом ВПН-а, и роутер n8n по нему выбирает
нужного бота.

### Как подключить новый ВПН

**Настройки → Сервисы → Добавить сервис.** Четыре поля:

| Поле | Что вписать |
|---|---|
| Название | как показывать ВПН операторам |
| Адрес API бота | `https://<хост>/<bot_id>/api/v1` — Support API этого бота |
| Токен | токен того же бота |
| `business_id` | `business_connection_id` аккаунта поддержки из Telegram |

Кнопка **«Проверить подключение»** дёргает `GET /meta` и показывает, какой бот
ответил на этот токен и какие скоупы выданы. Нажмите её до сохранения: опечатку
в токене дешевле увидеть здесь, чем на первом клиенте.

Всё остальное заполняется само и лежит под «Дополнительно»: слаг (из названия),
коллекция Qdrant `kb_<слаг>`, префикс идентификаторов диалогов `<слаг>_`, цвет,
эмодзи и отдельный вебхук n8n. Слаг после создания не меняется.

Дальше остаётся раздать **флаги операторов** (Настройки → Операторы) и залить
**базу знаний с промптом** — они пер-сервисные, вкладки настроек показывают
плашку с текущим ВПН-ом.

**Про n8n.** Если бот один на все аккаунты поддержки, там менять нечего: сервис
определяется по `business_id` из сообщения, и новый ВПН заработает сразу после
сохранения формы. Если у ВПН-а свой бот — скопируйте комплект воркфлоу,
поставьте credentials этого бота и задайте `TG_TOKEN`, `SERVICE_SLUG`,
`KB_COLLECTION`; подробности в `n8n/README.md`.

### Как панель понимает, чей это тикет

`business_id` во входящем событии → сервис (`app/rabbitmq_consumer.py`,
`_resolve_service`). Если поля нет — по слагу в поле `service`, как раньше; если
нет и его — первый сервис.

**Неизвестный `business_id` событие отбрасывает** и пишет в лог, какой именно.
Так задумано: свалить тикет чужого ВПН-а в первый попавшийся хуже, чем не
принять его. Увидели такую строку — впишите id в карточку сервиса.

Один `business_id` может принадлежать только одному сервису; в базе это
стережёт частичный уникальный индекс, в панели — понятная ошибка при
сохранении.

### Отдельный инстанс n8n на сервис

Если у ВПН-а свой n8n, укажите его адрес в поле «Вебхук n8n» у сервиса —
исходящие события этого ВПН-а пойдут туда вместо общего `N8N_WEBHOOK_URL`.
Очередь `vpn_bot.incoming` при этом остаётся общей: события разбираются по полю
`service`, а префикс `dialog_id` не даёт идентификаторам разных инстансов
столкнуться.

### Миграция существующей установки

При первом запуске новой версии создаётся сервис по умолчанию
(`DEFAULT_SERVICE_SLUG` / `DEFAULT_SERVICE_NAME`, по умолчанию `gruvpn` /
«GruVPN»), и на него переносятся все существующие диалоги, статьи БЗ, шаблоны и
настройки. Коллекция Qdrant у него остаётся прежней — `kb`, префикс
`dialog_id` пустой, поэтому переиндексация базы знаний не нужна и старые ссылки
на диалоги продолжают работать. Всем существующим операторам проставляется флаг
на этот сервис. Миграция одноразовая, помечена флагом `multi_tenant_v1`.

Воркфлоу n8n, которые ещё не передают `service`, продолжают работать: событие
без этого поля относится к первому сервису.

## Мониторинг: серверы и боты

Вкладка «Состояние» показывает серверы и ботов **каждого ВПН-сервиса
отдельно**. Доступна всем операторам: каждый видит только те ВПН-ы, на которые
у него есть флаг. В режиме «Все сервисы» — секция на каждый сервис плюс общий
итог.

> ⚠ **Сейчас данные — мок.** Реальный источник не подключён: серверы и боты
> выдуманы. Это помечено флагом `isMock` в API, жёлтым баннером над экраном,
> бейджем `MOCK` на каждой карточке и строкой «источник: mock». Как подключить
> настоящий — ниже.

### Как это устроено

Один контракт — `HealthProvider` (`app/health.py`). Провайдер отвечает за один
вид компонентов одного сервиса и возвращает список `ComponentStatus`:

| Провайдер | Вид | Что делает |
|---|---|---|
| `infra` | серверы | **боевой источник** — клиент вашей infra-API |
| `infra_bots` | боты | **боевой источник** — клиент вашей infra-API |
| `mock` | серверы | МОК: выдуманные серверы со случайными метриками |
| `mock_bot` | боты | МОК: выдуманные боты сервиса |
| `tcp` | серверы | запасной вариант: доступность по TCP-порту + пинг |
| `http` | серверы | запасной вариант: health-эндпоинт с JSON `{"load": …, "uptime": …}` |

Какой источник работает у конкретного ВПН-а — пер-сервисная настройка
`monitoring` (лежит в том же механизме, что `ai_settings` / `automation`):

```json
{
  "interval": 300,
  "servers": {"provider": "tcp", "config": {"servers": [
      {"name": "Frankfurt-01", "host": "1.2.3.4", "port": 443, "location": "DE"}
  ]}},
  "bots": {"provider": "mock_bot", "config": {}}
}
```

Меняется в панели: «Состояние» → блок «Источник данных» (виден администратору),
либо через `PUT /api/settings/monitoring?service_id=N`.


### Подключение вашей infra-API

Состояние серверов и ботов даёт ваш сервис инфраструктуры — панель к нему
подключается как клиент (`app/infra.py`). Настройка на ВПН:

```json
{
  "servers": {"provider": "infra",      "config": {"base_url": "https://infra.example.com", "token": "…"}},
  "bots":    {"provider": "infra_bots", "config": {"base_url": "https://infra.example.com", "token": "…"}}
}
```

Панель делает `GET {base_url}/api/servers?service=<слаг>` (и `/api/bots`),
токен уходит как `Authorization: Bearer`. Пути, имя заголовка и имя параметра
меняются в конфиге (`servers_path`, `bots_path`, `auth_header`,
`service_param`).

Ожидаемый ответ — массив либо объект с `items` / `data` / `results`:

```json
{"items": [
  {"id": "fra-01", "name": "Frankfurt-01", "status": "ok", "location": "DE",
   "message": "", "metrics": {"load": 42.5, "ping": 12.3, "uptime": 99.9}}
]}
```

**Подгонять формат на стороне инфраструктуры не нужно** — соответствие полей
описывается в конфиге:

```json
"mapping":     {"id": "node_id", "name": "title", "status": "state",
                "location": "region", "message": "note"},
"metrics_map": {"load": "cpu_pct", "ping": "rtt_ms", "uptime": "uptime_pct"},
"status_map":  {"online": "ok", "degraded": "high", "offline": "down"}
```

Статусы `online/up/healthy/active`, `degraded/warning/overloaded`,
`offline/failed/stopped` распознаются без настройки; незнакомый статус даёт
`unknown` и подписывает, какое значение пришло. Недоступность infra-API,
неверный токен или пустой ответ не роняют экран: на их месте карточка
`unknown` с причиной, остальные источники продолжают опрашиваться.

### Свой источник данных, если понадобится

Положите файл в `app/providers/` — он подхватится при старте автоматически,
править существующий код не нужно:

```python
# app/providers/mypanel.py
from app.health import SERVERS, ComponentStatus, HealthProvider, register_provider

class MyPanelProvider(HealthProvider):
    """Моя панель: состояние нод по HTTP API."""
    kind, source = SERVERS, "mypanel"

    async def check(self) -> list[ComponentStatus]:
        data = await fetch(self.config["url"], self.config["token"])
        return [
            self.make(n["id"], n["name"], "ok" if n["alive"] else "down",
                      location=n.get("region", ""),
                      metrics={"load": n["cpu"], "ping": n["rtt"]})
            for n in data["nodes"]
        ]

register_provider("mypanel", MyPanelProvider)
```

После перезапуска `mypanel` появляется в выборе источника в панели — фронт
править тоже не нужно, список строится из реестра.

Статусы: `ok` — норма, `high` — работает на пределе, `down` — не отвечает,
`unknown` — проверить не удалось. Провайдер, который упал или не
зарегистрирован, не роняет опрос остальных: на его месте появляется карточка
`unknown` с причиной.

### Уведомления о падении

Переход компонента в `down` шлёт `server_down` (или `bot_down` для ботов) в
n8n — **боту того ВПН-а**, чей компонент лёг. Уведомление приходит только на
переходе, чтобы лежащий сервер не слал его каждый цикл; первое наблюдение
после старта не уведомляет — это защита от шторма при перезапуске.

### Миграция

Прежние глобальные `SERVERS` / `SERVERS_MONITOR_TYPE` / `SERVERS_CHECK_INTERVAL`
из `.env` при первом запуске переносятся в настройку `monitoring` первого
сервиса (флаг `monitoring_v1`) — установка с настроенным мониторингом не
откатывается на мок. Эндпоинт `GET /api/servers` заменён на `GET /api/health`.

## Карточка клиента: подключение своего API

Правая колонка в «Диалогах» показывает профиль клиента и даёт управлять его
аккаунтом: ключи, рефералы, бан, реф.баланс, сообщение в основного бота (тот,
что выдаёт ключи, а не бот техподдержки). Данные и действия живут во внешней
системе — панель знает только канонический вид, описанный в `app/customer.py`.

Источник задаётся **на каждый ВПН-сервис** в «Настройки → Клиенты». По
умолчанию — `mock`: выдуманные данные, помеченные в интерфейсе, чтобы панель
работала до интеграции.

### Что видит и делает оператор

| Вкладка | Содержимое |
|---------|------------|
| Профиль | ссылка на ник, tg id, язык, статус, группа, тариф, подписка, пробный период, партнёр, реф.процент, реф.баланс, реф.код, депозиты, трафик |
| Ключи | ключ: сервер, тариф, срок, трафик, устройства; выдать / заменить / удалить / ±дни |
| Рефералы | список приглашённых, сколько оплатили, сумма их депозитов; привязать по tg id и отвязать |
| История | прошлые обращения клиента |

Опасные действия — **бан, разбан, «сделать партнёром», изменение реф.баланса и
удаление ключа** — доступны только роли `admin`; агент их не видит. Каждое
выполненное действие пишется в переписку системным сообщением («кто и что
сделал»), так что журнал — это история тикета.

### Вариант 1: свой REST без единой строчки кода

Выберите источник `http` и опишите его в JSON-конфиге настройки:

```json
{
  "base_url": "https://infra.example.com",
  "token": "секрет",
  "auth_header": "Authorization",
  "service_param": "service",
  "paths":   { "profile": "GET /v2/users/{chat_id}" },
  "mapping": { "plan": "tariff", "ref_balance": "referral_balance" },
  "keys_mapping":      { "expires_at": "valid_until" },
  "referrals_mapping": { "tg_id": "telegram_id" },
  "deposits_field": "payments",
  "deposits_mapping": { "amount": "sum" },
  "disable": ["set_partner"]
}
```

- `paths` — если ваши адреса отличаются от умолчаний. Формат `МЕТОД /путь`,
  подставляются `{chat_id}`, `{key_id}`, `{tg_id}`. Полный список умолчаний —
  `_DEFAULT_PATHS` в `app/customers.py`.
- `mapping` и `*_mapping` — соответствие «наше поле → ваше»; подгонять API под
  панель не нужно.
- `disable` — что ваша система не умеет: такие кнопки оператору не показываются.

Ответ профиля может быть завёрнут в `data` / `user` / `customer` / `result` —
обёртка разворачивается сама.

### Готовый источник: Support API бота

Основной источник для установок, где есть Telegram-бот с этим API. Покрывает
карточку целиком, включая то, чего нет в Remnawave: балансы, депозиты,
рефералов, промокоды, пробный период, язык — и отправку сообщения клиенту
в тот же чат, где он общается с ботом. В VPN-панель API ходит сам.

Источник `bot_api`, конфиг:

```json
{
  "base_url": "https://host/nemoivpn/api/v1",
  "token": "токен этого бота",
  "timeout": 20,
  "notify": true,
  "default_server_id": null,
  "default_days": 30
}
```

Адрес отличается только сегментом `<bot_id>`, поэтому шесть ботов — это шесть
ВПН-сервисов в панели, у каждого свой `base_url` и свой токен. **Один токен на
несколько ботов использовать нельзя**: базы ботов не связаны, один и тот же
Telegram ID в разных ботах — разные люди.

| Поле карточки | Источник |
|---|---|
| Профиль | `GET /users/resolve?value=<chat_id>` — почти всё одним быстрым запросом |
| Рефералы | `GET /users/{tgid}/referrals` |
| Депозиты | `GET /users/{tgid}/payments` |
| Устройства | `GET /keys/{id}` активного ключа |
| Ключи | `keys[]` из профиля |

Действия: бан и разбан (`PATCH` `blocked`), партнёрский процент, реф.баланс,
сообщение клиенту, выдача и удаление ключа, продление и сокращение срока,
пересоздание, включение и выключение, смена локации, отвязка одного устройства
и сброс всех.

Не реализованы: привязка и отвязка реферала (эндпоинтов нет), докупка трафика
(лимит общий на бота, задаётся в `meta`), сброс ключа (дублирует
пересоздание). Кнопки не показываются.

**Пять мест, где легко ошибиться:**

1. **`banned` и `blocked` — не то, что кажется.** По их справочнику `banned`
   означает «прошёл капчу и допущен к боту», а блокировка администратором —
   это `blocked`. Кнопка «Забанить» пишет `blocked`; читать `banned` как
   «забанен» нельзя, иначе все обычные клиенты окажутся забаненными.
2. **Успешный код не значит успех.** `delivered: false` при отправке
   сообщения, `ok: false` в ActionResult, `panel_error` в карточке ключа,
   `error` в состоянии сервера — всё это приходит с `200`. Провайдер
   разворачивает их в неуспех, чтобы оператор не увидел «Готово» там, где
   ничего не произошло.
3. **Баланс меняется дельтой и не идемпотентен.** Повтор запроса при таймауте
   начислит второй раз — не ретраить. Режим «установить значение» в карточке
   провайдер пересчитывает в дельту, читая текущий баланс.
4. **`GET /keys/{id}` ходит в панель дважды и медленный.** Профиль строится из
   `resolve`, а полная карточка ключа с устройствами запрашивается только для
   активного ключа. Поэтому счётчик «Устройств» заполнен у активного ключа, а
   у остальных стоит «—»: это «не спрашивали», а не «устройств нет». Лимит
   частоты — 600 запросов в минуту на токен.
5. **`X-Operator` — ваш оператор в их аудите.** Панель проставляет имя
   залогиненного человека, и в их `GET /audit` видно, кто именно нажал кнопку.

**Порядок безопасного подключения.** Сначала `GET /meta` как проверка связи —
он покажет `bot_id` и выданные скоупы. Затем только чтение: в конфиг `disable`
со всеми действиями, открыть тикет и сверить профиль с ботом. Здесь же
проверяется фактический смысл `banned` на живых данных. Потом действия на
своём аккаунте, начиная с сообщения и продления; бан, удаление ключа и
реф.баланс — последними.

### Готовый источник: Remnawave

Провайдер `remnawave` (`app/providers/remnawave.py`) подключается выбором
источника в «Настройки → Клиенты» и конфигом:

```json
{
  "base_url": "https://panel.example.com",
  "token": "токен из /api/tokens",
  "timeout": 10,
  "telegram_filter": "telegramId",
  "default_days": 30,
  "default_squad_uuid": ""
}
```

Токен идёт как `Authorization: Bearer`. Логин через `/api/auth/login` не нужен —
API-токены Remnawave подходят напрямую, но у них есть скоупы: read-only токен
даст 403 на любое действие.

| Поле карточки | Remnawave |
|---|---|
| Telegram ID | `telegramId` |
| Статус | `status`: ACTIVE / DISABLED / LIMITED / EXPIRED |
| Тариф | `tag`, иначе имена из `activeInternalSquads` |
| Группа | `externalSquadUuid` |
| След. платёж | `expireAt` |
| Трафик | `userTraffic.usedTrafficBytes` / `trafficLimitBytes`, **байты → ГБ** |
| Ключи | сами пользователи Remnawave |
| Устройства | `GET /api/hwid/devices/{userId}` |

**«Ключ» — это пользователь Remnawave.** У каждого свои `shortUuid`,
`subscriptionUrl`, срок и лимит трафика, поэтому несколько подписок одного
клиента — это несколько записей с одним `telegramId`, и они становятся списком
на вкладке «Ключи». Поля профиля берутся с первой активной, трафик суммируется
по всем.

**Чего в Remnawave нет.** Ни рефералов, ни реф.баланса, ни депозитов,
партнёрства, языка и пробного периода — поиск по спецификации даёт ноль
вхождений; `/api/infra-billing/*` это расходы на хостинг нод, а не платежи
клиентов. Соответствующие методы в провайдере не переопределены, поэтому
карточка не показывает эти кнопки, а поля остаются пустыми. Когда появится API
бота-магазина, недостающее подключается вторым источником.

**Две тонкости, на которых легко ошибиться:**

- `{userId}` в путях — числовой `id`, а не `shortUuid` и не UUID.
- «Убавить время» через `actions/extend` невозможно: у `days` стоит
  `minimum: 1`. Провайдер для отрицательных дней читает `expireAt` и пишет
  пересчитанный через `PATCH /api/users` — единственное место, где одно
  действие превращается в два запроса.

**Порядок безопасного подключения.** Сначала только чтение: в конфиг
`"disable": ["ban","unban","key_issue","key_add_time","key_replace",
"key_delete","renew","buy_traffic","reset_key"]`, открыть тикет и сверить срок,
трафик и статус с веб-интерфейсом панели. Здесь же проверяется
`telegram_filter`: если имя колонки не совпало, список приходит пустым и
карточка скажет «в Remnawave нет пользователя с таким Telegram ID». Затем
завести тестового пользователя со своим Telegram ID, снять `disable` и
прогнать действия на нём. Опасные — в последнюю очередь.

### Вариант 2: свой провайдер файлом

Когда логика сложнее маппинга — положите модуль в `app/providers/`, он
подхватится при старте. Реализуйте `fetch()` и только те действия, которые
поддерживает ваша система: список кнопок в интерфейсе строится по
переопределённым методам.

```python
from app.customer import ActionResult, CustomerProfile, CustomerProvider, KeyInfo, register_customer_provider

class MyCrmProvider(CustomerProvider):
    """Моя CRM: профиль клиента и управление ключами."""
    source = "mycrm"

    async def fetch(self, chat_id: str) -> CustomerProfile: ...
    async def options(self, chat_id: str) -> dict: ...      # серверы и тарифы для форм
    async def key_issue(self, chat_id, days=30, server="", plan=""): ...

register_customer_provider("mycrm", MyCrmProvider)
```

Действия в контракте: `key_issue`, `key_add_time` (отрицательные дни убавляют
срок), `key_replace`, `key_delete`, `referral_link`, `referral_unlink`, `ban`,
`unban`, `set_partner`, `set_ref_balance`, `send_message`, `renew_subscription`,
`buy_traffic`, `reset_key`. Формы под них панель строит по описанию полей в
`ACTIONS` — новое действие добавляется правкой только бэкенда.

### Устойчивость

Профиль кэшируется на `cacheTtl` секунд (по умолчанию 60) и сбрасывается после
любого успешного действия. Если внешняя API недоступна или источник не
зарегистрирован, тикет всё равно открывается: панель показывает снапшот из
нашей БД (то, что прислал n8n вместе с сообщениями) с пометкой «данные могут
устареть» и причиной.

### Миграция

Прежний глобальный биллинг (`BILLING_API_URL` / `BILLING_API_TOKEN` в `.env`,
модуль `app/billing.py`, эндпоинт `POST /api/dialogs/{id}/billing/{action}`)
поглощён этим контрактом. При первом запуске адрес и токен переносятся в
настройку `customer` первого сервиса с провайдером `http` (флаг `customer_v1`),
три прежних действия остаются доступными.

## Панель на телефоне

Отдельной мобильной сборки нет: те же `app/static/*.jsx`, раскладка ветвится по
ширине окна. Хук `useViewport()` (`app/static/components.jsx`) даёт три режима:

| Режим | Ширина | Диалоги | Карточка клиента |
|-------|--------|---------|------------------|
| `mobile`  | < 700px       | список **или** переписка (drill-down) | шторка снизу |
| `tablet`  | 700–1099px    | две колонки: список + переписка       | шторка снизу |
| `desktop` | ≥ 1100px      | три колонки, как раньше               | правая колонка |

Что меняется на телефоне:

- **Верхняя навигация и ряд пилюль сервисов скрываются.** Вместо них — шапка
  экрана (`MobileAppBar`), лента сервисов плитками (`ServiceRail`, тот же
  `/api/services` со счётчиками) и нижняя навигация (`MobileNav`).
- **Список диалогов** — «Мои/Все» отдельным переключателем плюс прокручиваемые
  чипы разделов; поиск прячется под кнопку-лупу в шапке.
- **Переписка** открывается тапом по строке, «назад» возвращает к списку;
  нижняя навигация на время переписки уступает место композеру и клавиатуре.
  Действия над тикетом (взять, передать, в ожидание, вернуть в очередь,
  закрыть) собраны в шторку по кнопке «⋯».
- **Шаблоны по слешу** работают так же: кнопка шаблонов ставит `/` и открывает
  ту же панель автодополнения, выбор — тапом.
- **Настройки** — список с провалами вместо бокового меню; таблицы операторов
  и сервисов показываются карточками.
- Колокольчик уведомлений живёт в шапке каждого экрана, меню профиля (пауза,
  выход) — в шапке «Настроек»; оба открываются шторкой `BottomSheet`.

Учтены `env(safe-area-inset-bottom)` под нижнюю навигацию и композер и `100dvh`,
чтобы поле ввода не уезжало под клавиатуру. Цели нажатия в шапке, ленте
сервисов, чипах и нижней навигации — не меньше 44×44 CSS-пикселей.

|---|---|
| Приём Telegram-вебхука | Telegram API-интеграция без кода |

```
1. Пользователь пишет в Telegram
2. n8n: Telegram Trigger получает webhook
3. n8n: создаёт/находит диалог в n8n_dialogs (PostgreSQL)
4. n8n: если есть медиа — скачивает файл и загружает на наш сервер POST /api/n8n/upload
5. n8n: LPUSH в Redis-очередь vpn_bot:incoming (JSON с типом user_message)
6. Python: RabbitMQConsumer читает сообщение из очереди
7. Python: upsert диалога и сохранение сообщения в БД
8. Python: WebSocket broadcast — все операторы видят новое сообщение
9. Python: фоновая задача — классификация сообщения по категории
10. Python: если новый диалог — PUBLISH в vpn_bot:notifications (уведомление операторов)
11. Если ai_status=true для диалога → n8n вызывает AI Agent воркфлоу
```

assigned_operator     TEXT      — имя назначенного оператора (NULL = в очереди)
ai_enabled            BOOL      — включён ли AI
operator_called       BOOL      — пользователь нажал «позвать оператора»
rating                SMALLINT  — оценка 1–5 (звёзды), NULL если не оценён
unread_count          INT       — счётчик непрочитанных
user_name/username    TEXT      — имя и @username
user_plan             TEXT      — тариф: Basic / Pro / ...
user_sub_status       TEXT      — active | expired | ...
user_next_payment     TEXT      — дата следующего платежа
user_traffic_used/total FLOAT  — использованный и общий трафик (ГБ)
last_payment_amount/date TEXT  — последний платёж
last_message_text     TEXT      — превью последнего сообщения
```

**`messages`** — сообщения в диалоге:

```
dialog_id     TEXT     — ссылка на dialogs
kind          TEXT     — user | ai | operator | system
text          TEXT     — текст сообщения
file_id       TEXT     — Telegram file_id
file_type     TEXT     — photo | document | voice
file_url      TEXT     — URL файла на сервере (/api/files/...)
operator_name TEXT     — имя оператора если kind=operator
category      TEXT     — категория (заполняется классификатором)
```

**`operators`** — учётные записи операторов:

```
name          TEXT   — отображаемое имя
tg            TEXT   — @username (используется для логина)
tg_id         BIGINT — Telegram user ID (нужен для уведомлений)
role          TEXT   — admin | agent
password_hash TEXT
online        BOOL
initials      TEXT   — аватар (первые буквы имени)
color         TEXT   — цвет аватара
notif_prefs   TEXT   — JSON настройки уведомлений
```

**`settings`** — ключ-значение для настроек:

```
key=ai_settings   → JSON: prompt, temperature, auto_reply, handoff_enabled, classification_enabled
key=schedule      → JSON: {"mon": {"enabled": true, "from": "09:00", "to": "21:00"}, ...}
key=automation    → JSON: max_tickets_per_operator, operator_button_enabled, operator_button_after_msgs
```

**`kb_articles`** — метаданные чанков базы знаний:

```
id, title, category, keywords, content (полный текст чанка)
```

**`message_templates`** — шаблоны быстрых ответов:

```
group_name, title, text
```

**Специальный маркер `[HANDOFF]`:** если AI добавляет этот маркер в ответ, Python-сторона автоматически переключает диалог на оператора (выключает AI, устанавливает `operator_called=true`, меняет статус диалога).

### Воркфлоу 3: Output (Отправка пользователю)

Универсальный воркфлоу для отправки любого типа контента пользователю в Telegram. Вызывается из Main и AI Agent как `executeWorkflow`.

```
When Executed by Another Workflow
  Inputs: chat_id, message, file_id, file_type
    │
    ▼
Switch: file_type
    │
    ├── "photo"   → HTTP Request (скачать файл по file_id как binary)
    │               Send a photo message
    │                   Telegram sendPhoto + binary data
    │                   caption = message
    │
    ├── "sticker" → Send a sticker
    │                   Telegram sendSticker
    │                   file = file_id (оригинальный Telegram file_id)
    │
    ├── "voice"   → HTTP Request2 (Telegram getFile по file_id)
    │               HTTP Request3 (скачать OGG по result.file_path)
    │               HTTP Request4 (POST sendVoice multipart/form-data)
    │
    └── [text/default] → Send a text message
                             Telegram sendMessage
                             parse_mode = HTML
```

> **Важно:** для фото/голоса загруженных оператором через веб-панель `file_id` содержит URL нашего сервера (`https://yourdomain.com/api/files/...`). Для стикеров от пользователей — передаётся оригинальный Telegram `file_id` напрямую.

**Тип `user_message`:**

  "chat_id": "123456789",
  "message": "Привет",

  "operator_called": false,
  "user_name": "Иван Иванов",
  "user_username": "@ivan",
  "user_plan": "Pro",
  "user_sub_status": "active",
  "user_next_payment": "2025-06-01",
  "user_traffic_used": 45.2,
  "user_traffic_total": 100,
  "user_last_payment_amount": "299",
  "user_last_payment_date": "2025-05-01"
}
```

**Тип `ai_response`:**
```json
{
  "type": "ai_response",
  "dialog_id": "42",
  "message": "[HANDOFF] Передаю вас оператору, он скоро ответит."
}
```

> Если в тексте AI-ответа есть `[HANDOFF]` — Python автоматически переводит диалог
> к оператору (auto-handoff) и вырезает маркер из сохранённого сообщения. В n8n
> клиенту текст отправляется тоже без маркера (см. `n8n/ai-agent.json` — нода
> `Call 'Main Output'`).
>
> **Стоп-слова (гарантированная передача).** Независимо от решения ИИ: если клиент
> пишет в ИИ-диалог сообщение, содержащее любое из стоп-слов (настройка
> «Автоматизация → Стоп-слова вызова оператора», по умолчанию «оператор, менеджер,
> живой человек, реальный человек, поддержк»), бэкенд сразу передаёт тикет оператору
> с причиной «клиент попросил оператора». Нюанс: ИИ может успеть ответить на это же
> сообщение один раз (событие уже ушло в n8n параллельно), дальше ИИ отключён.
>
> Порядок обновления: задеплоить бэкенд → импортировать `n8n/ai-agent.json` в n8n
> (заменяет AI-воркфлоу) → пересохранить ИИ-настройки в панели (обновит промпт в Redis).

**Callback от пользователя (inline-кнопка):**
```json
{
  "type": "callback",
  "callback_data": "call_op:42"
}
```

| `callback_data` | Что делает Python |
|---|---|
| `call_op:{dialog_id}` | Помечает `operator_called=true`, уведомляет оператора |
| `rate:{dialog_id}:{1-5}` | Сохраняет оценку в `dialogs.rating` |

**Уведомление операторам:**

| `event` | Поля | Смысл |
|---|---|---|
| `new_dialog` | `dialog_id`, `username` | Пришёл новый тикет |

`schedule_notify` — уведомления с учётом рабочих часов:
- В рабочее время → немедленная отправка
- Вне рабочих часов → ставится в `vpn_bot:pending_notifications`
- При следующей отправке в рабочее время — очередь сбрасывается

## n8n: настройка воркфлоу

Готовые шаблоны лежат в каталоге **`n8n/`** — четыре воркфлоу, составляющие
связку «Telegram ↔ панель». Подробная инструкция там же, в `n8n/README.md`.

| Файл | Что делает |
|------|-----------|
| `n8n/main-input.json` | Telegram Trigger → буфер → таблицы n8n → панель |
| `n8n/main-output.json` | Отправка в Telegram + подтверждение доставки |
| `n8n/outgoing-router.json` | Webhook от панели → ответ оператора, уведомления, статусы |
| `n8n/ai-agent.json` | ИИ-агент с базой знаний и гейтом передачи оператору |

### Всё пер-сервисное вынесено в переменные n8n

Токен бота **не должен** быть вписан в URL нод: при ротации придётся править
десяток мест, и он утекает вместе с экспортом воркфлоу. В шаблонах везде
`{{ $vars.TG_TOKEN }}`. Settings → Variables:

| Переменная | Пример | Откуда |
|-----------|--------|--------|
| `SERVICE_SLUG` | `gruvpn` | Настройки → Сервисы, «Слаг» |
| `TG_TOKEN` | `1234567890:AAF…` | @BotFather этого бота |
| `KB_COLLECTION` | `kb` | Настройки → Сервисы, «Коллекция Qdrant» |
| `PANEL_URL` | `https://admin.example.com/files` | `BASE_URL` + `BASE_URL_PATH`, если задан |
| `N8N_API_KEY` | случайная строка | то же значение, что в `.env` панели |

### Подключить нового бота

1. Панель: Настройки → Сервисы → создать ВПН. Слаг после первого запуска
   менять нельзя — он в ключах Redis, поле `service` и имени коллекции Qdrant.
2. В карточке сервиса заполнить «n8n Webhook URL» — исходящие пойдут туда,
   а не на общий `N8N_WEBHOOK_URL`.
3. n8n: импортировать четыре воркфлоу, задать переменные, в `Telegram Trigger`
   выбрать credential нового бота, активировать.

Один комплект воркфлоу = один бот = один ВПН-сервис. Держать один комплект на
все ВПН-ы и определять сервис по `bot_id` из триггера тоже можно, но это
заметно больше правок — при втором боте проще скопировать комплект.

### Контракт с панелью — не менять

- Очереди `vpn_bot.incoming` / `vpn_bot.outgoing`, путь вебхука
  `vpn-bot-outgoing`.
- Имя ноды `Распарсить JSON` — на неё ссылаются по имени через `$('…')`.
- Поля `user_message`: `type, service, dialog_id, chat_id, user_username,
  user_name, message, ai_enabled, file_id, file_type`.
- Поля `delivery_confirmation`: `type, message_id, dialog_id, status, error`.
  Без них в панели не появятся галочки доставки.
- Значения `type` исходящих: `manager_message`, `send_to_user`,
  `operator_notify`.

**Поле `service` обязательно.** Без него панель не знает, какому ВПН-у
принадлежит событие, и сваливает всё в первый сервис — см.
`_resolve_service` в `app/rabbitmq_consumer.py`.

### Грабли, на которые легко наступить

- **Смешение токенов.** `getFile` возвращает `file_path`, действительный
  только для того же токена. Скачивать и отправлять надо одним ботом, иначе
  файлы приходят битыми или не приходят вовсе.
- **`ai_enabled` из неверного поля.** В `n8n_dialogs` есть и `status`
  (`active`/`closed`), и `ai_status` (boolean). Если отправить `status`,
  панель получит строку `"active"`, посчитает её истиной, и выключенный
  оператором ИИ включится обратно на следующем сообщении клиента.
- **Ключ настроек ИИ.** Панель пишет `vpn_bot:<slug>:ai_settings`. Старый
  глобальный `vpn_bot:ai_settings` больше не заполняется: воркфлоу молча
  уедет на дефолты с **пустым системным промптом**.
- **Коллекция Qdrant.** У каждого ВПН-а своя; зашитая `kb` означает, что
  второй сервис ищет по чужой базе знаний.
- **`n8n_dialogs.service`.** Панель обновляет статус диалога и `ai_status`
  с фильтром по `service` (`app/database.py`, `sync_n8n_dialog_status`).
  Если колонка не заполнена при вставке, закрытие тикета и переключение ИИ
  из панели до n8n не доходят.

### 3. Загрузка файлов на наш сервер

В HTTP Request узлах загрузки фото/голоса (Main воркфлоу) нужно добавить заголовок для авторизации:
```
X-API-Key: {значение N8N_API_KEY из .env}
```

URL загрузки: `POST https://yourdomain.com/api/n8n/upload`

| Тип | Как работает |
|---|---|
| `tcp` | TCP-подключение к `host:port`, измеряет пинг |
| `http` | GET `host:port/health`, читает `load` и `uptime` из JSON |
| `stub` | Фиктивные данные для разработки |

### Своя логика проверки

```python
# app/servers.py
class MyMonitor(ServerMonitor):
    async def check_one(self, server: ServerInfo) -> ServerResult:
        data = await my_api.get_server_stats(server.host)
        return ServerResult(
            name=server.name, location=server.location,
            status="ok" if data["alive"] else "down",
            load=data.get("cpu_pct"),
            ping=data.get("latency_ms"),
            uptime=data.get("uptime_pct"),
        )
```

Зарегистрировать в `main.py` вместо `make_server_monitor(...)`.

## Файлы пользователей

Telegram-файлы нельзя отобразить в браузере по `file_id`. Схема:

```
1. Пользователь → Telegram файл
2. n8n скачивает через Telegram API
3. n8n POST /api/n8n/upload  (multipart + X-API-Key: N8N_API_KEY)
4. Python сохраняет → { "url": "/api/files/abc123.jpg" }
5. n8n включает file_url в Redis-сообщение
6. Браузер отображает: <img src="/api/files/abc123.jpg">
```

Оператор → пользователь:
```
Оператор прикрепляет файл в браузере
→ POST /api/upload → URL
→ URL + сообщение → vpn_bot:outgoing
→ n8n скачивает URL, отправляет в Telegram
```

### S3-хранилище

Если заданы `S3_BUCKET` и `S3_ACCESS_KEY` — файлы сохраняются в S3 вместо локального диска. Совместимо с AWS S3, Cloudflare R2, MinIO, Yandex Object Storage.

### Запуск (`main.py`)

При старте выполняется в порядке:
1. Загрузка настроек из `.env` (Pydantic Settings)
2. Инициализация пула соединений PostgreSQL
3. Автомиграции БД (idempotent `ALTER TABLE IF NOT EXISTS`)
4. Создание первого администратора (если задан `ADMIN_INIT_TG`)
5. Инициализация: Redis, WebSocket-менеджер, n8n-клиент, биллинг, мониторинг серверов
6. Параллельный запуск трёх задач через `asyncio.gather()`:
   - Uvicorn (FastAPI + WebSocket)
   - RabbitMQConsumer (очередь `vpn_bot.incoming`)
   - ServerMonitor (периодическая проверка серверов)

## REST API (краткий справочник)

### Аутентификация

| Метод | Путь | Описание |
|-------|------|---------|
| GET | `/api/auth/status` | Нужна ли начальная настройка |
| POST | `/api/auth/setup` | Создать первого администратора |
| POST | `/api/auth/login` | Войти (tg + password) → JWT токен |
| GET | `/api/auth/me` | Текущий оператор |
| PUT | `/api/auth/password` | Сменить пароль |

JWT токен передаётся в заголовке `Authorization: Bearer <token>` или через WebSocket query `?token=<token>`.

### Диалоги

|-------|------|---------|

| GET | `/api/dialogs/{id}/history` | Предыдущие тикеты от этого пользователя |
